# 客户端说明（桌面端 + 移动端）

客户端是**端侧离线**的原生应用：业务引擎、数据库与材料生成全部在本机完成，不需要服务器、不产生外部请求。

- 技术栈：Avalonia UI 12 + .NET 10，复用现有 `Domain / Application / Infrastructure / AI / Documents / ProjectScan` 引擎
- 平台覆盖：

  | 平台 | 状态 | 说明 |
  |---|---|---|
  | Windows | ✅ 已交付 | 自包含发布 + Inno Setup 安装包模板 |
  | macOS | ⚠️ 工程可发布 | 签名包需在 Mac 上用 Xcode 打包 |
  | Linux | ⚠️ 工程可发布 | 签名包需在 Linux 上打包 |
  | Android | ✅ 已产出 APK | `scripts/build-mobile.ps1`；未在真机/模拟器上跑过 |
  | iOS | ⏳ 未产出 | 同一套代码加 `net10.0-ios` 目标即可，但必须在 Mac 上签名 |
  | 鸿蒙 | ❌ 本期不做 | 鸿蒙 NEXT 没有 .NET 运行时，需独立 ArkTS 工程与签名链 |

## 一、为什么能复用同一套引擎

搬之前先确认过一件事：**业务引擎本来就不依赖 ASP.NET**。

| 项目 | 依赖 | 结论 |
|---|---|---|
| `SoftCopyright.Domain` | 仅 BCL | 可直接复用 |
| `SoftCopyright.Application` | Domain | 可直接复用 |
| `SoftCopyright.Infrastructure` | Domain + Application（含 EF Core、SQLite、文件存储、后台任务） | 可直接复用 |
| `SoftCopyright.AI` / `Documents` / `ProjectScan` | Domain | 可直接复用 |
| `SoftCopyright.Api` / `SoftCopyright.Web` | ASP.NET Core / Razor | **只有这两层是 Web 专属**，客户端不需要 |

用例服务本身也不依赖 HTTP 契约：

- `ICaseUploadService.UploadAsync(caseId, fileName, Stream, ct)` —— 收的是流，客户端直接 `File.OpenRead` 即可
- `ICurrentAccountContext.Use(userId)` —— Web 端由中间件写入，客户端由组合根写入
- `ISecretProtector` / `IPasswordHasher` —— 密钥文件与密码派生都在本机，不变

所以客户端不是"把 Web 再写一遍"，而是**换一个宿主**：把引擎装进本机进程，把 Web 的 HTTP 边界换成进程内调用。

## 二、工程结构

```
src/SoftCopyright.Client/        # 共享界面与引擎组合（net10.0 类库）
  App.axaml / App.axaml.cs       # 主题与设计令牌（深浅双套）、生命周期分发
  Themes/Controls.axaml          # 控件样式
  ViewModels/                    # MVVM（CommunityToolkit.Mvvm）
  Views/
    ShellView.axaml(.cs)         # 应用外壳：顶栏 + 侧栏/底部导航 + 内容区 + 状态栏
    MainWindow.axaml(.cs)        # 桌面端窗口（只是给 ShellView 套一层窗口）
    CasesView / ImportView / AnalysisView / ApplicantView / CodeView / MaterialsView
  Services/
    DesktopEngine.cs             # 端侧组合根：无 ASP.NET 的 DI + 本机库 + 后台任务
    AppBootstrap.cs              # 启动期共享状态
    ThemeService.cs              # 深浅主题切换与偏好持久化
    DesktopLaunchOptions.cs      # --case / --step / --demo / --snapshot / --size
    DemoSeeder.cs                # 演示数据

src/SoftCopyright.Desktop/       # 桌面端宿主（net10.0，WinExe）
  Program.cs, app.manifest, appsettings.json

src/SoftCopyright.Mobile/        # Android 宿主（net10.0-android）
  Application.cs, MainActivity.cs, Properties/AndroidManifest.xml, Resources/
```

`ShellView` 是关键：桌面端由 `MainWindow` 承载它，Android 端整屏显示它——
**同一套界面与视图模型，只有外壳不同**。

### 生命周期差异

| 平台 | Avalonia 生命周期 | 外壳 |
|---|---|---|
| 桌面 | `IClassicDesktopStyleApplicationLifetime` | `MainWindow`（窗口） |
| Android | `IActivityApplicationLifetime` | `ShellView`（单视图，整屏） |

`App.OnFrameworkInitializationCompleted` 按生命周期类型分发，两端共用同一段初始化逻辑。

## 三、端侧与 Web 的差异

| 关注点 | Web 端 | 客户端 |
|---|---|---|
| 数据库 | MySQL（服务器） | **本机** SQLite（Windows: `%LOCALAPPDATA%\SoftCopyright`；Android: 应用内部存储目录） |
| 账号 | 注册 / 登录 / Cookie | 单用户：本机内置管理员，案例全部归属它，界面没有登录页 |
| 调用方式 | 界面 → HTTP → API → 用例 | 界面 → 视图模型 → **直接调用**用例 |
| 模型接入 | 账号级配置 + 全局环境变量 | 同一套账号级配置（密钥加密后存本机库），不配就是完全离线 |
| 界面 | Razor / Blazor | Avalonia / MVVM |

校验规则、材料生成器、选项目录这些"业务事实"只有一份，客户端直接复用，没有第二套实现。

## 四、启动顺序（容易踩坑）

引擎必须在 **Avalonia 初始化之前**就绪。在 UI 线程上阻塞等待异步任务会与 Avalonia 的同步上下文死锁：

```csharp
// Program.Main：此时还没有 Avalonia 同步上下文，阻塞等待是安全的
AppBootstrap.PrepareEngine(args);
BuildAvaloniaApp().StartWithClassicDesktopLifetime(args);
```

Android 端同理，放在 `MainActivity.OnCreate` 的 `base.OnCreate` 之前。

同样地，**先建库再启动后台任务**：后台任务执行器一上来就会查任务表，库还没迁移就会报 `no such table: BackgroundJobs`。

```csharp
var host = builder.Build();
// 先迁移数据库，再 Start —— 顺序反了后台任务会先炸
await DatabaseInitializer.InitializeAsync(db, logger, ct);
await host.StartAsync(ct);
```

### 迁移快照与 SQLite

迁移快照是按 **MySQL** 提供程序生成的（里面记录的是 MySQL 的默认类型映射）。换到 SQLite 后逐项比对必然出现差异——这是提供程序差异，不是真实的结构变更。SQLite 的类型系统更宽松，同一套迁移脚本可以直接套用，因此只在 SQLite 分支关闭了这条告警（`InfrastructureServiceExtensions.ConfigureDatabase`）。

## 五、响应式：同一套界面适配宽屏与窄屏

| 位置 | 宽屏（桌面） | 窄屏（手机） |
|---|---|---|
| 导航 | 左侧栏，六个步骤 | 底部导航：上一步 / 当前步骤 / 下一步 |
| 申请信息表单 | 流式布局自动排成多列 | 自动变单列 |
| 顶栏 | 全称 + 模型接入 + 主题 + 数据目录 | 短标题 + 主题 |
| 状态栏 | 状态 + 数据目录路径 | 只显示状态 |

实现方式：

- 窄屏判定放在 `ShellView.UpdateCompact()`（窗口宽度 < 900 逻辑像素即切窄屏），结果写进 `ShellViewModel.IsCompact`；
- 表单用 `WrapPanel` 流式排布，字段组固定 300 逻辑像素宽——宽屏排三列，窄屏自然折成一列，不需要两套 XAML。

## 六、运行与打包

```powershell
# 开发运行
dotnet run --project src/SoftCopyright.Desktop

# 生成演示案例（用仓库里的样例仓库，含一份示例申请信息）
dotnet run --project src/SoftCopyright.Desktop -- --demo

# 直接打开指定案例的指定步骤
dotnet run --project src/SoftCopyright.Desktop -- --case <案例 ID> --step Applicant

# 按手机尺寸开窗，检查窄屏布局
dotnet run --project src/SoftCopyright.Desktop -- --size 390x844

# 把当前窗口渲染成 PNG（文档截图与界面自查用，不受屏幕分辨率影响）
dotnet run --project src/SoftCopyright.Desktop -- --case <案例 ID> --step Applicant --snapshot out.png
```

桌面端发布：

```powershell
# Windows（自包含，目标机器不需要装 .NET）
./scripts/publish-desktop.ps1 -Platform windows

# Windows 安装包（需要本机装有 Inno Setup 6）
./scripts/publish-desktop.ps1 -Platform windows -Installer

# Linux / macOS
./scripts/publish-desktop.ps1 -Platform linux
./scripts/publish-desktop.ps1 -Platform macos
```

移动端发布：

```powershell
# 前置：安装 .NET Android 工作负载
dotnet workload install android

./scripts/build-mobile.ps1
```

产物落在 `artifacts/`（不纳入版本控制）。APK 用 `adb install -r <apk 路径>` 安装。

## 七、界面

- **深浅双主题**：设计令牌与 Web 端同一套语义，`App.axaml` 里用 `ThemeDictionaries` 给两套取值，切换即时生效并记在本机 `ui-preferences.json`
- **申请信息页**按官方申请表的分区排布；八个官方规定选项渲染为下拉，候选项直接来自 `ApplicantOptionCatalog`（不在界面里硬编码）
- **条件字段**紧跟触发它的选项：选了「修改软件」就出现「修改说明」，选了「已发表」就出现「首次发表日期 / 地点」；「原始取得 + 非单独开发」的冲突会在开发方式下方直接提示

## 八、测试

`tests/SoftCopyright.Tests/Integration/DesktopEngineTests.cs` 直接驱动 `DesktopEngine`，验证**没有 ASP.NET、没有 HTTP** 的情况下整条链路能跑通：

- 端侧引擎在不启动服务器的情况下跑通完整软著闭环（新建 → 导入 ZIP → 扫描 → 分析 → 确认画像 → 填申请信息 → 确认 → 选代码 → 确认 → 生成材料 → 读出材料包）
- 端侧引擎拒绝不在候选项之内的申请信息
- 端侧引擎拒绝格式非法的分类号
- 无服务器时仍能解析本机账号与模型接入状态（未配置密钥时必须是完全离线）
- 启动参数能指定案例与步骤
- 演示数据能生成带样例申请信息的案例

## 九、已知边界

- **Android 未在真机上跑过**。APK 能构建、能签名，但本机没有模拟器或设备，运行时行为（尤其是文件对话框与内部存储路径）没有实测。
- **iOS 未产出**。Avalonia 的 iOS 后端可用，但需要在 macOS 上签名与打包，Windows 上产出不了。
- **鸿蒙本期不做**。鸿蒙 NEXT 不支持 .NET 运行时，也不能装 Android APK；要做只能另起 ArkTS 工程并重写引擎。如后续要覆盖，建议评估 ArkUI-X（复用 Android 构建）。
- **桌面端当前只覆盖软著线**。专利线在引擎层已经就绪（`PatentMaterialFlow` 等），但界面尚未实现，需要补「专利交底书」与「专利材料」两个步骤。
- **迁移快照以 MySQL 为准**。客户端用 SQLite 跑同一套迁移；如果以后要支持其他提供程序，需要单独一套迁移程序集。
- **客户端是单用户**。没有登录页与多账号隔离；需要多人协作时仍应使用 Web 端。
