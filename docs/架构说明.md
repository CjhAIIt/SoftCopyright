# 架构说明

## 一、总体结构

模块化单体（Modular Monolith）。**同一套引擎有两个宿主**：Web 端（浏览器访问，需要服务器）与原生客户端（端侧离线，不需要服务器）。

```text
┌──────────────────────────────┐      ┌──────────────────────────────┐
│ SoftCopyright.Api            │      │ SoftCopyright.Client         │
│ ASP.NET Core 宿主            │      │ 原生客户端共享层             │
│ Minimal API + Blazor Web App │      │ 界面(MVVM) + 端侧引擎组合根   │
└───────────┬──────────────────┘      └───────┬──────────┬───────────┘
            │ HTTP                            │ 进程内直接调用
   ┌────────▼────────┐                        │
   │ SoftCopyright.  │                        │
   │ Web（界面）     │──HTTP──────────────────▶│
   └─────────────────┘                        │
            │                                  │
            └──────────┬───────────────────────┘
                       ▼
        ┌──────────────────────────────────────────┐
        │ SoftCopyright.Application：用例编排        │
        │  上传 / 扫描 / 分析 / 确认门禁 / 校验 / 生成 │
        └───────────────────┬──────────────────────┘
                            │ 仅依赖 Domain 契约
   ┌──────────────┬─────────┴────────┬──────────────┐  实现层
   │ ProjectScan  │ AI               │ Documents    │
   │ 安全解包     │ 三个 Provider    │ DOCX/TXT/ZIP  │
   │ 扫描/适配器  │ 证据包/校验      │              │
   └──────────────┴──────────────────┴──────┬───────┘
                                           ▼
        ┌──────────────────────────────────────────┐
        │ SoftCopyright.Domain                     │
        │ 实体、值对象、枚举、配置项、契约、选项目录 │
        │ 零外部依赖，是所有模块共同依赖的"内核"     │
        └──────────────────────────────────────────┘

        ┌──────────────────────────────────────────┐
        │ SoftCopyright.Infrastructure             │
        │ EF Core 10 + MySQL 8.0 / SQLite / 文件存储  │
        │ 后台任务 Worker / 密码派生 / 密钥保护       │
        └──────────────────────────────────────────┘

   宿主外壳（只负责启动，不含业务逻辑）：
   ┌──────────────────────┐  ┌──────────────────────┐
   │ SoftCopyright.Desktop│  │ SoftCopyright.Mobile  │
   │ Windows/macOS/Linux  │  │ Android               │
   │ MainWindow → ShellView│  │ Activity → ShellView │
   └──────────────────────┘  └──────────────────────┘
```

`SoftCopyright.Client` 是关键：它把界面与端侧组合根放在一起，**桌面端与 Android 端引用同一份源码**。
桌面端由 `MainWindow` 承载 `ShellView`，Android 端整屏显示 `ShellView`（单视图生命周期）。
详见 [`客户端说明.md`](客户端说明.md)。

## 二、依赖方向（单向，禁止反向引用）

| 项目 | 允许依赖 |
|---|---|
| `Domain` | 无（仅 BCL） |
| `Application` | `Domain` |
| `ProjectScan` | `Domain` |
| `AI` | `Domain` |
| `Documents` | `Domain` |
| `Infrastructure` | `Domain`、`Application` |
| `Api` | 以上全部 |
| `Web` | `Domain`、`Application`（**不得**直接访问数据库） |
| `Client` | `Domain`、`Application`、`Infrastructure`、`AI`、`Documents`、`ProjectScan`（**不得**依赖 `Api` / `Web`） |
| `Desktop` / `Mobile` | `Client` + 引擎层 |

**引擎层不得引入 ASP.NET 依赖**——这是客户端复用引擎的前提。
`Api` 与 `Web` 是仅有的两个 Web 专属层，`Client` 一行都不碰。

跨模块协作一律通过 `Domain` 中的接口契约完成（端口与适配器风格）：

- 扫描契约：`IProjectScanService`、`IProjectAdapter`、`ISafeArchiveExtractor`、`IProjectFileReader`
- AI 契约：`IProjectAnalyzer`、`IMaterialDraftGenerator`、`IAiProvider`、`IEvidencePackBuilder`、`IAiOutputValidator`
- 专利契约：`IPatentService`、`IPatentDraftGenerator`、`IPatentDocumentGenerator`
- 账号契约：`IAccountService`、`ICurrentAccountContext`、`IPasswordHasher`、`ISecretProtector`、`IAiSettingsProvider`
- 文档契约：`IMaterialDocumentGenerator`、`IMaterialPackageBuilder`
- 用例契约：`ICaseService`、`IApplicantInfoService`、`ICodeSelectionService`、`IConfirmationService`、`IValidationService`
- 工作流契约：`ICaseUploadService`、`ICaseScanWorkflow`、`ICaseAnalyzeWorkflow`、`ICaseGenerationWorkflow`、`ICasePatentDraftWorkflow`
- 基础设施契约：`IRepository<T>`、`IFileStore`、`IBackgroundJobQueue`

### 申请信息的选项型字段

官方申请表里有 8 个栏位本应是**选项**而不是自由填写。这类知识属于领域事实，放在 `Domain` 的
`ApplicantOptionCatalog` 里，由三处共用同一份定义：

| 使用方 | 用途 |
|---|---|
| `Api` | `GET /api/softcopyright/applicant-options` 下发候选项、条件必填与跨字段约束 |
| `Application` | `ApplicantOptionChecker` 统一判定：保存时拒绝非法取值，校验规则集出具 `R-FIELDS-02` |
| `Documents` | 生成申请表信息时把规范选项码还原成官方中文标签 |

数据库存**规范选项码**而不是中文文本，显示文本由目录解析；历史自由文本写法通过别名表归一化，
避免旧案例因措辞调整而失效。详见 [`软著申请字段规范.md`](软著申请字段规范.md)。

### 端侧组合根

`SoftCopyright.Client/Services/DesktopEngine.cs` 是客户端的组合根：它把同一批用例服务装进本机进程，
数据落在本机 SQLite，**不经过 HTTP**。

| 关注点 | Web 端 | 客户端 |
|---|---|---|
| 组合根 | `Api/Program.cs`（ASP.NET 宿主） | `Client/Services/DesktopEngine.cs`（Generic Host） |
| 数据库 | MySQL（服务器） | 本机 SQLite |
| 账号作用域 | `AccountScopeMiddleware` 按登录态写入 | 组合根启动时写入本机账号 |
| 后台任务 | `BackgroundJobWorker`（Hosted Service） | 同一个 Worker，在本机进程内跑 |
| 文件访问 | `IFileStore` 落到数据目录 | 同一个 `IFileStore`，只是数据目录换成本机位置 |

客户端调用的是**同一批用例服务**（`ICaseService`、`IApplicantInfoService`、`ICodeSelectionService`、
`IConfirmationService`、`IValidationService`、`ICaseGenerationWorkflow`），因此不存在
「客户端一套校验、服务器另一套校验」的问题。

**启动顺序**（两条都写在代码里，别改反）：引擎必须在 Avalonia 初始化**之前**就绪（UI 线程阻塞等待异步任务会死锁），
且必须**先迁移数据库再启动后台任务**（否则 `no such table: BackgroundJobs`）。

### 两条材料流程如何分开

软著登记与专利申请是两条**相互独立的业务流程**。差异不在共享代码里到处 `if`，而是收敛到成对的实现中，由注册表按 `ApplicationCase.MaterialKind` 挑选：

| 关注点 | 契约 | 软著实现 | 专利实现 |
|---|---|---|---|
| 流程描述 | `IMaterialFlowDescriptor` | `SoftCopyrightMaterialFlow` | `PatentMaterialFlow` |
| 校验规则集 | `IMaterialValidationRuleSet` | `SoftCopyrightValidationRuleSet` | `PatentValidationRuleSet` |
| 产物生成策略 | `IMaterialGenerationStrategy` | `SoftCopyrightGenerationStrategy` | `PatentGenerationStrategy` |
| 确认门禁 | `IConfirmationGate` | `SoftCopyrightConfirmationGate` | `PatentConfirmationGate` |

`IMaterialFlowDescriptor` 定义阶段文案、页面标签、产物清单、是否需要勾选代码范围、材料包文件名与工作区路径。`Web` 通过 `GET /api/flows` 取这份描述渲染界面，因此前端同样不硬编码两条流程的差异。

| 环节 | 软著登记 | 专利申请 |
|---|---|---|
| 事实来源 | 项目画像 + 申请信息 | 项目画像 + **技术交底书**（唯一真源） |
| 前置门禁 | 画像 → 申请信息 → 代码范围 | 画像 → 交底书 → 权利要求已生成 |
| 生成产物 | 申请表信息 / 操作手册 / 代码鉴别材料 / 证据清单 / 校验报告 / ZIP | 权利要求书 / 说明书 / 摘要 / 技术交底书 / ZIP |
| 校验规则 | `R-` 前缀 | `P-` 前缀（叠加在通用规则之上） |

专利案例**不要求**勾选代码范围，因为专利申请文件不含代码鉴别材料，技术特征直接来自扫描证据。两条流程的**阶段槽位**复用同一批枚举值（`CaseStage`），差异只体现在文案上，避免为专利再开一套状态机。

### 账号、认证与模型接入

账号只存在于本机数据库，材料按账号隔离。

| 环节 | 实现 |
|---|---|
| 密码 | `IPasswordHasher`（基础设施层实现）：PBKDF2-HMAC-SHA256，21 万次迭代，存盐与派生值，不存明文 |
| 登录态 | ASP.NET Core Cookie 认证；HttpOnly + SameSite=Lax；API 未登录返回 401 而非跳转 |
| 敏感配置 | `ISecretProtector`：AES-256-GCM，机器密钥放在数据目录（`secret.key`），不在仓库内 |
| 账号作用域 | `ICurrentAccountContext`：Web 请求由中间件按登录态写入；后台任务由工作流按案例归属账号显式指定 |
| 模型接入 | `IAiSettingsProvider`：先取当前账号在引导流程中的配置，取不到再回退到全局环境变量配置 |

因为后台任务没有 HttpContext，`BackgroundJobWorker` 会先按案例找到归属账号并写入作用域，之后 AI 层才能解析到**该账号**的模型接入设置。

**认证切分**：登录与注册页是静态 SSR 表单，直接 POST 到 `/api/auth/*`，`Set-Cookie` 才直达浏览器；Blazor 界面回调自身 API 时由 `CookieForwardingHandler` 转发当前请求的 Cookie。

**归属守卫**：案例按账号隔离。所有带案例 ID 的端点统一挂 `CaseOwnershipFilter`，在处理器之前校验"该案例对当前账号可见"，不可见即返回 404（不区分"不存在"与"无权限"）。产物下载端点按产物回溯到案例后同样校验。

**配置绑定**：`IConfiguration` 对数组属性是**追加**而不是**替换**。选项类里给了默认值、配置文件里又写了同名项时会叠加成重复列表，因此统一走 `OptionsBinder.Bind`：绑定前清空数组、绑定后对未配置的项还原默认值。

**管理端**：`/api/admin/*` 要求 `Admin` 角色。内置管理员账号在启动时幂等创建（仓库只存密码哈希），管理员可查看全部账号、删除账号、查看数据总览；管理员不能删除自己，系统至少保留一个管理员。

## 三、端到端数据流

```text
上传 ZIP
  └─ UploadService
       ├─ IFileStore.SaveUploadAsync     写入 cases/{id}/upload/
       └─ ISafeArchiveExtractor          安全解包到 cases/{id}/extracted/
            └─ 归档被拒 → 记录原因、返回 400

Git 仓库导入（GitHub / Gitee / GitLab）
  └─ GitImportService
       ├─ GitRepositoryUrl.TryParse      地址解析 + 域名白名单 + 注入防护
       ├─ IGitRepositoryImporter         只读克隆（禁钩子/禁 LFS/禁 ext::）
       ├─ 克隆后删除 .git，校验工作区大小上限
       ├─ 记录来源仓库与提交号
       └─ 自动排队扫描任务

扫描（后台任务 Scan）
  └─ ScanWorkflow
       ├─ IProjectScanService.ScanAsync
       │    ├─ 文件索引：路径 / 大小 / SHA-256 / 文本判定 / 编码 / 语言 / 行数
       │    ├─ 排除规则（可配置）+ 安全排除（不可取消）
       │    ├─ 密钥检测 → 标记排除
       │    ├─ 适配器链：dotnet → node → python → java → miniprogram → generic
       │    └─ 生成 ProjectProfile / Coverage / OpenQuestions
       ├─ 落库 ProjectFile / Evidence / ProjectAnalysis
       └─ 失效下游确认与已生成产物

智能分析（后台任务 Analyze，可选）
  └─ AnalyzeWorkflow
       ├─ IEvidencePackBuilder            脱敏 + 截断 + 限量
       ├─ IProjectAnalyzer                规则 / 模型 / 回退
       ├─ IMaterialDraftGenerator         章节标题（不含代码）
       └─ 合并功能条目与开放问题

填写申请信息 → 保存
  └─ ApplicantInfoService
       ├─ 乐观并发（RowVersion）
       ├─ 字段来源标注（申请人输入 / 仓库证据 / AI 推断 / 已确认）
       └─ 失效下游确认与产物

选择代码范围 → 保存
  └─ CodeSelectionService
       ├─ 只接受候选列表内的路径
       ├─ 计算 ConfirmedHash（路径集合 + 文件哈希）
       └─ 失效下游确认与产物

生成材料（后台任务 Generate）
  └─ GenerationWorkflow
       ├─ 从被确认文件读取真实代码（逐行，不改写）
       ├─ IValidationService              一致性校验
       ├─ IMaterialDocumentGenerator      8 份产物
       ├─ IFileStore.SaveArtifactAsync    落盘 + 登记产物索引
       └─ IMaterialPackageBuilder         打包 ZIP
```

## 四、关键设计取舍

| 取舍 | 理由 |
|---|---|
| 契约放在 `Domain` 而不是各实现模块 | 保证 `Application` 不反向依赖实现层，同时保持单向依赖 |
| 事实与证据分离存储 | 申请人确认数据落 `ApplicantInfo`，模型推断落 `ProjectAnalysis.ProfileJson`，两者永不互相覆盖 |
| 确认内容哈希而非"版本号" | 直接对"被确认的数据"取哈希，上游任何改动都会让下游确认失效，无需手工维护失效规则 |
| 原始 SQL 只用于任务原子认领 | 需要"只有状态仍为 Pending 才生效"的语义；其余一律走 EF LINQ，避免方言差异 |
| 文件路径全部由服务端生成 | 客户端永远不能提交磁盘路径，杜绝路径穿越与越权下载 |
| EF 迁移而非 `EnsureCreated` | `EnsureCreated` 不会演进已有库的结构，新增列会直接报 `Unknown column`；改用迁移后结构变更由迁移脚本负责，升级不需要删库 |
| 迁移快照按 MySQL 生成，SQLite 复用同一套脚本 | 快照里记录的是提供程序的默认类型映射，换提供程序比对必然出差异；SQLite 类型系统更宽松，直接套用同一套脚本，只在 SQLite 分支关掉模型差异告警 |
| DateTimeOffset 统一转 UTC DateTime 存储 | SQLite 不支持按 DateTimeOffset 排序比较，MySQL 也不存偏移量；统一为 UTC 后两种数据库行为一致 |
| 引擎层不依赖 ASP.NET | 这是客户端复用引擎的前提；`Client` 直接引用引擎层，进程内调用，不经过 HTTP |
| 界面只写一份，靠 `IsCompact` + `WrapPanel` 适配宽窄屏 | 桌面端与手机端共用 `ShellView`；窄屏收起侧栏改底部导航，表单流式折行，不需要两套 XAML |
