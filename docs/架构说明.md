# 架构说明

## 一、总体结构

模块化单体（Modular Monolith），单进程同时承载 API 与 Blazor 界面，不做微服务拆分。

```text
┌──────────────────────────────────────────────────────────────┐
│ SoftCopyright.Api（ASP.NET Core 宿主）                       │
│   Minimal API 端点 + Blazor Web App（Interactive Server）     │
│   统一错误响应 / 健康检查 / 全局异常映射                     │
└───────────┬──────────────────────────────┬───────────────────┘
            │                              │
   ┌────────▼────────┐            ┌────────▼─────────┐
   │ SoftCopyright.  │            │ SoftCopyright.   │
   │ Web（界面）     │──HTTP────▶ │ Application      │
   └─────────────────┘            └────────┬─────────┘
                                             │ 仅依赖 Domain 契约
   ┌──────────────┬──────────────┬──────────▼─────────┐
   │ ProjectScan  │ AI           │ Documents          │  实现层
   │ 安全解包     │ 三个 Provider│ DOCX/TXT/JSON/ZIP   │
   │ 扫描/适配器  │ 证据包/校验  │                     │
   └──────────────┴──────────────┴──────────┬─────────┘
                                             │
   ┌─────────────────────────────────────────▼───────────────┐
   │ SoftCopyright.Domain：实体、值对象、枚举、配置项、契约    │
   │ 零外部依赖，是所有模块共同依赖的"内核"                    │
   └─────────────────────────────────────────────────────────┘

   ┌─────────────────────────────────────────────────────────┐
   │ SoftCopyright.Infrastructure                            │
   │ EF Core 10 + MySQL 8.0 / 文件存储 / 后台任务 Worker      │
   └─────────────────────────────────────────────────────────┘
```

## 二、依赖方向（单向，禁止反向引用）

| 项目 | 允许依赖 |
|---|---|
| `Domain` | 无（仅 BCL） |
| `Application` | `Domain` |
| `ProjectScan` | `Domain` |
| `AI` | `Domain` |
| `Documents` | `Domain` |
| `Infrastructure` | `Domain`、`Application` |
| `Api` | 以上全部 |
| `Web` | `Domain`、`Application`（**不得**直接访问数据库） |

跨模块协作一律通过 `Domain` 中的接口契约完成（端口与适配器风格）：

- 扫描契约：`IProjectScanService`、`IProjectAdapter`、`ISafeArchiveExtractor`、`IProjectFileReader`
- AI 契约：`IProjectAnalyzer`、`IMaterialDraftGenerator`、`IAiProvider`、`IEvidencePackBuilder`、`IAiOutputValidator`
- 专利契约：`IPatentService`、`IPatentDraftGenerator`、`IPatentDocumentGenerator`
- 文档契约：`IMaterialDocumentGenerator`、`IMaterialPackageBuilder`
- 用例契约：`ICaseService`、`IApplicantInfoService`、`ICodeSelectionService`、`IConfirmationService`、`IValidationService`
- 工作流契约：`ICaseUploadService`、`ICaseScanWorkflow`、`ICaseAnalyzeWorkflow`、`ICaseGenerationWorkflow`、`ICasePatentDraftWorkflow`
- 基础设施契约：`IRepository<T>`、`IFileStore`、`IBackgroundJobQueue`

### 材料类型分流

`ApplicationCase.MaterialKind` 决定同一套流水线产出哪类材料，其余环节（扫描、证据、确认门禁框架、校验中心）完全复用：

| 环节 | 软著登记 | 专利申请 |
|---|---|---|
| 事实来源 | 项目画像 + 申请信息 | 项目画像 + **技术交底书**（唯一真源） |
| 前置门禁 | 画像 → 申请信息 → 代码范围 | 画像 → 交底书 → 权利要求已生成 |
| 生成产物 | 申请表信息 / 操作手册 / 代码鉴别材料 / 证据清单 / 校验报告 / ZIP | 权利要求书 / 说明书 / 摘要 / 技术交底书 / ZIP |
| 校验规则 | `R-` 前缀 | `P-` 前缀（叠加在通用规则之上） |

专利案例**不要求**勾选代码范围，因为专利申请文件不含代码鉴别材料，技术特征直接来自扫描证据。

## 三、端到端数据流

```text
上传 ZIP
  └─ UploadService
       ├─ IFileStore.SaveUploadAsync     写入 cases/{id}/upload/
       └─ ISafeArchiveExtractor          安全解包到 cases/{id}/extracted/
            └─ 归档被拒 → 记录原因、返回 400

Git 仓库导入（GitHub / Gitee / GitLab）
  └─ GitImportService
       ├─ GitRepositoryUrl.TryParse      地址解析 + 域名白名单 + 注入防护
       ├─ IGitRepositoryImporter         只读克隆（禁钩子/禁 LFS/禁 ext::）
       ├─ 克隆后删除 .git，校验工作区大小上限
       ├─ 记录来源仓库与提交号
       └─ 自动排队扫描任务

扫描（后台任务 Scan）
  └─ ScanWorkflow
       ├─ IProjectScanService.ScanAsync
       │    ├─ 文件索引：路径 / 大小 / SHA-256 / 文本判定 / 编码 / 语言 / 行数
       │    ├─ 排除规则（可配置）+ 安全排除（不可取消）
       │    ├─ 密钥检测 → 标记排除
       │    ├─ 适配器链：dotnet → node → python → java → miniprogram → generic
       │    └─ 生成 ProjectProfile / Coverage / OpenQuestions
       ├─ 落库 ProjectFile / Evidence / ProjectAnalysis
       └─ 失效下游确认与已生成产物

智能分析（后台任务 Analyze，可选）
  └─ AnalyzeWorkflow
       ├─ IEvidencePackBuilder            脱敏 + 截断 + 限量
       ├─ IProjectAnalyzer                规则 / 模型 / 回退
       ├─ IMaterialDraftGenerator         章节标题（不含代码）
       └─ 合并功能条目与开放问题

填写申请信息 → 保存
  └─ ApplicantInfoService
       ├─ 乐观并发（RowVersion）
       ├─ 字段来源标注（申请人输入 / 仓库证据 / AI 推断 / 已确认）
       └─ 失效下游确认与产物

选择代码范围 → 保存
  └─ CodeSelectionService
       ├─ 只接受候选列表内的路径
       ├─ 计算 ConfirmedHash（路径集合 + 文件哈希）
       └─ 失效下游确认与产物

生成材料（后台任务 Generate）
  └─ GenerationWorkflow
       ├─ 从被确认文件读取真实代码（逐行，不改写）
       ├─ IValidationService              一致性校验
       ├─ IMaterialDocumentGenerator      8 份产物
       ├─ IFileStore.SaveArtifactAsync    落盘 + 登记产物索引
       └─ IMaterialPackageBuilder         打包 ZIP
```

## 四、关键设计取舍

| 取舍 | 理由 |
|---|---|
| 契约放在 `Domain` 而不是各实现模块 | 保证 `Application` 不反向依赖实现层，同时保持单向依赖 |
| 事实与证据分离存储 | 申请人确认数据落 `ApplicantInfo`，模型推断落 `ProjectAnalysis.ProfileJson`，两者永不互相覆盖 |
| 确认内容哈希而非"版本号" | 直接对"被确认的数据"取哈希，上游任何改动都会让下游确认失效，无需手工维护失效规则 |
| 原始 SQL 只用于任务原子认领 | 需要"只有状态仍为 Pending 才生效"的语义；其余一律走 EF LINQ，避免方言差异 |
| 文件路径全部由服务端生成 | 客户端永远不能提交磁盘路径，杜绝路径穿越与越权下载 |
| `EnsureCreated` 而非 EF 迁移 | MVP 避免额外安装 `dotnet-ef` 全局工具；正式化时再切换到迁移脚本 |
| DateTimeOffset 统一转 UTC DateTime 存储 | SQLite 不支持按 DateTimeOffset 排序比较，MySQL 也不存偏移量；统一为 UTC 后两种数据库行为一致 |
