# 状态机与确认门禁

## 一、阶段状态机

```text
Created → Uploaded → Scanning → AnalysisReady → ApplicantInfoPending
        → CodeSelectionPending → DraftReady → ReviewPending → Validating
        → PackageReady → Archived
```

| 阶段 | 含义 | 进入方式 |
|---|---|---|
| `Created` | 案例已创建，等待导入 | 用户创建 |
| `Uploaded` | ZIP 已安全解包，等待扫描 | 上传成功 |
| `Scanning` | 后台扫描进行中 | 用户触发扫描 |
| `AnalysisReady` | 项目画像与证据就绪 | 扫描成功 |
| `ApplicantInfoPending` | 待填写申请信息 | **门禁1** 项目画像确认 |
| `CodeSelectionPending` | 待选择代码范围 | **门禁2** 申请信息确认 |
| `DraftReady` | 草稿内容就绪，待审阅 | **门禁3** 代码范围确认 |
| `ReviewPending` | 草稿已确认，待生成正式材料 | **门禁4** 文档草稿确认 |
| `Validating` | 正在生成并校验材料 | 生成任务启动 |
| `PackageReady` | 材料包已生成，可下载 | 生成与校验完成 |
| `Archived` | 全部确认完成 | **门禁5** 最终材料确认 |
| `Failed` | 某个环节失败，可重试 | 任意阶段失败 |

### 迁移规则

- 只允许沿主流程**相邻**迁移，禁止跨阶段跳跃（例如 `Uploaded → PackageReady` 会被拒绝）；
- 任意阶段都可进入 `Failed`，并记录失败原因；
- `Failed` 可以回到任意在途阶段以便重试；
- 迁移集中定义在 `Application/Services/CaseWorkflow.cs`，API 与工作流共用同一份规则。

## 二、五道人工确认门禁

| # | 阶段 | 前置条件 | 确认内容 |
|---|---|---|---|
| 1 | 项目画像 | 扫描完成 | 软件名、版本、用途、功能条目、覆盖情况、待补充问题 |
| 2 | 申请信息 | 已填写申请信息，且**选项字段全部落在官方候选项之内** | 全部申请字段，特别是法律与权属字段 |
| 3 | 代码范围 | 已勾选源文件 | 纳入材料包的文件集合及其哈希 |
| 4 | 文档草稿 | 门禁 1–3 均已确认且未失效 | 草稿所依据的全部上游数据 |
| 5 | 最终材料 | 材料包已生成且未失效 | 全部产物内容 |

未通过前置条件时，API 返回 **409** 并给出明确的中文原因，例如：

```json
{ "error": { "code": "conflict", "message": "请先填写并确认申请信息，再生成材料。" } }
```

**门禁 2 的选项字段约束**：申请信息里有 8 个栏位是官方规定的**选项**（软件来源、开发方式、发表状态、
权利取得方式、权利范围、著作权人类别、申请办理方式、鉴别材料交存方式），不能自由填写。
保存时越界直接 400；缺项、条件必填未满足、跨字段冲突（如「原始取得」却选了「合作开发」）
由校验规则 `R-FIELDS-02` 列为「需申请人处理」，不出现在校验报告的「通过」里。
详见 [`软著申请字段规范.md`](软著申请字段规范.md)。

> **Web 端与客户端的门禁是同一套**：`IConfirmationService` 与 `ConfirmationGateRegistry` 都在 `Application` 层，
> 客户端直接调用它们，不另写一套规则。

## 三、确认记录

每次确认写入 `ConfirmationRecord`：

| 字段 | 含义 |
|---|---|
| `Stage` | 确认的门禁阶段 |
| `ConfirmedBy` | 确认人（MVP 固定为「本地用户」） |
| `ConfirmedAt` | 确认时间 |
| `DataHash` | **被确认数据的规范化哈希** |
| `Note` | 确认说明 |
| `InvalidatedAt` / `InvalidatedReason` | 显式失效记录（审计用） |

## 四、内容哈希与失效判定

`IsStale` **不在数据库里存**，而是在读取时实时比对，避免状态漂移。

哈希链设计（上游变动自然传导到下游）：

```text
profileHash  = H(画像语义内容)
applicantHash = H(profileHash, 申请信息全部字段)
codeHash     = H(applicantHash, 所选路径集合 + 各文件 SHA-256)
draftHash    = H(profileHash, applicantHash, codeHash, 规则版本)
finalHash    = H(profileHash, applicantHash, codeHash, 全部产物 SHA-256)
```

| 阶段 | 比对对象 |
|---|---|
| 项目画像确认 | `profileHash` |
| 申请信息确认 | `applicantHash` |
| 代码范围确认 | `codeHash` |
| 文档草稿确认 | `draftHash` |
| 最终材料确认 | `finalHash` |

### 失效级联

| 上游变化 | 失效的下游确认 | 已生成产物 |
|---|---|---|
| 重新扫描（画像变化） | 申请信息 → 代码范围 → 草稿 → 最终材料 | 全部标记 `IsStale`，禁止下载 |
| 修改申请信息 | 申请信息 → 代码范围 → 草稿 → 最终材料 | 全部标记 `IsStale` |
| 修改代码范围 | 代码范围 → 草稿 → 最终材料 | 全部标记 `IsStale` |

失效后必须重新走一遍对应门禁才能继续生成或下载。

## 五、后台任务

| 项 | 语义 |
|---|---|
| 存储 | 持久化任务表 `BackgroundJobs`，不是内存队列 |
| 认领 | 单条原子 `UPDATE ... WHERE Status='Pending'`，只有一次认领成功 |
| 租约 | 执行中持有租约（默认 10 分钟），进程崩溃后租约过期自动回队 |
| 重试 | 最多 3 次，退避 5s / 15s / 45s；超过上限置 `Failed` 并记录原因 |
| 进度 | 由各阶段真实推进点更新，失败置 0；不做平滑假进度 |
| 幂等 | 同一案例同类任务在 `Pending/Running` 时不再重复创建 |

失败信息只保留异常类型与消息，**不写入堆栈与源码内容**，避免把仓库正文带进日志。

## 六、删除语义

`DELETE /api/cases/{id}`：

1. 写入一条删除审计摘要（案例名、文件数、产物数、确认数，**不含源码**）；
2. 删除案例及其全部关联数据库行；
3. 物理删除 `cases/{caseId}/` 目录（上传包、解包内容、全部产物）。

之后 `GET /api/cases/{id}`、`GET /api/cases/{id}/package/download`、`GET /api/artifacts/{id}/download` 一律返回 **404**。
